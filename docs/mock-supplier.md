# Mock Supplier 설계

Mock 자체의 코드 품질보다 **연동 견고성을 검증하는 유일한 수단**이라는 점이
중요하다 — 스펙과 어긋나면 검증 자체가 무의미해진다. 이 문서는 Mock이 지켜야
하는 규칙을 정리한다.

## 기본 원칙

1. **요구사항 문서의 스펙을 정확히 재현한다.** 필드 위치·타입·존재
   여부가 스펙과 달라지면 안 된다 (예: `breakfastIncluded`의 위치 — 아래
   "필드 위치" 참고). 스펙 원문 자체는 이 저장소에 옮겨 적지
   않는다 — 필요한 설계 판단만 우리 표현으로 남긴다.
2. **본 애플리케이션과 다른 포트(9090)에서 별도 프로세스로 뜬다.** 같은 포트에
   두면 앱이 자기 자신을 호출하는 구조가 되어 실제 연동 문제와 구분이 안 되는
   실패가 생긴다.
3. **요청 파라미터는 무시하고 고정 응답을 준다.** Mock의 목적은 "다양한 데이터
   재현"이 아니라 "3가지 상황(정상/장애/무응답) 재현"이므로 파라미터별 분기는
   불필요.
4. **모드는 공급사별로 독립적으로 전환 가능해야 한다.** A를 장애 상태로 두고
   B는 정상으로 두는 조합(부분 실패 검증에 필수) 등을 만들 수 있어야 한다.

## 모드 (공급사별 독립)

| 모드 | 동작 | 검증 목적 |
|---|---|---|
| `normal` | 숙소 목록(①)/재고·요금(②) 정상 응답 | 정상 흐름 |
| `error` | A: HTTP 5xx / B: HTTP 200 + 자체 실패 코드 | 실패 판정 통일 |
| `no-response` | 연결은 되나 매우 긴 지연(30초) 후 정상 응답 | 사실상 무응답 취급, 타임아웃 |
| `delay` | 지정한 초(`seconds`)만큼 대기한 뒤 정상 응답 | 타임아웃 경계값 검증 |

전환은 컨트롤 엔드포인트로:
```
POST /control/{a|b}/mode?value={normal|error|no-response|delay}
POST /control/{a|b}/mode?value=delay&seconds=6   # delay는 seconds로 지연 시간 지정(기본 5초)
```

`delay`는 `no-response`(고정 30초, "사실상 무응답")와 달리 지연 시간을 초 단위로
자유롭게 조절할 수 있어, 타임아웃 값의 경계(예: 타임아웃보다 짧으면 성공,
길면 실패)를 정확히 검증하는 용도로 쓴다. 근거: `docs/architecture.md`
"타임아웃 값".

숙소 목록 API(①)는 장애 모드를 걸지 않는다. 필요하면 같은 방식으로 확장 가능하지만,
"매핑 생성 단계 자체가 실패하면 어떻게 할지"는 별도 설계 판단(매핑 생성 로직
문서에서 다룸)이라 Mock의 책임 범위 밖으로 둔다.

## 필드 위치

`breakfastIncluded`는 숙소 목록(①) 응답엔 없고, 재고·요금(②) 응답의 객실 타입
레벨에 한 번만 존재한다 (날짜별 항목 안에는 없음) — 요구사항 문서 기준.

## 데이터 불변조건 (Mock 샘플 데이터가 지켜야 할 것)

Mock 데이터 자체는 자유롭게 구성해도 되지만, 아래는 **검증 목적상 반드시
지켜야** 실제로 의미 있는 테스트가 된다.

1. **①과 ②의 숙소/객실 타입 코드가 일치해야 한다.** 숙소 목록(①)에서 반환한
   코드가 재고·요금(②)에서도 동일하게 조회 가능해야 한다 — 안 그러면 매핑
   생성(①) → 검색 조회(②) 흐름 자체가 끊어진다.
2. **A와 B는 겹치는 실제 숙소를 각자 다른 코드로 표현한다.** (예: A의
   `A-10023`과 B의 `B77120`이 같은 실제 숙소) — "공급사가 다르면 내부 식별자도
   다르다"는 매핑 동작을 검색 API 테스트에서 확인하기 위함.
3. **A에만 있는 숙소를 최소 1개 포함한다.** (예: `Namsan Garden Stay`) — 한쪽
   공급사에만 있는 상품도 정상적으로 응답에 섞이는지 확인하기 위함.
4. **A/B의 `breakfastIncluded`를 서로 다른 값으로 둔다.** 같은 상품인데 조식
   포함 여부가 다르면, 표준 모델이 이 차이를 그대로 보존하는지 확인 가능.
5. **최소 한 객실 타입은 재고가 0인 날짜를 포함한다.** "예약 불가 상품도
   0으로 노출"하기로 한 결정(`docs/domain-model.md`)을 검증하려면 필요.
6. **재고 값은 날짜마다 달라야 한다.** (예: 3, 1, 5) — "N박 전체 예약 가능
   객실 수 = 기간 내 최솟값" 로직이 제대로 동작하는지, 최댓값이나 체크인일
   값만 잘못 반환하고 있는 건 아닌지 구분해서 검증하기 위함.

## 이 문서와 다르게 구현된 게 발견되면

Mock 코드가 이 문서와 어긋나면(예: `breakfastIncluded` 위치가 스펙과 다름),
**코드를 스펙에 맞게 고치는 게 우선이다.** Mock의 코드 품질 자체는 평가 기준이 아니지만,
스펙과 다른 Mock은 "연동 동작을 검증하는 수단"으로서 무의미해지기 때문이다.
