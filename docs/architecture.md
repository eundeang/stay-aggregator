# 아키텍처 설계 근거

`CLAUDE.md`에 있는 규칙들의 배경과 근거를 정리한 문서. 매 세션 자동 로드되지 않으므로
필요할 때만 참고.

## 패키지 구조: 왜 포트-어댑터 단순화 버전인가

공급사가 여러 개 붙는 구조라, "새 공급사 추가 시 무엇을 고쳐야 하는지"가 명확해야
한다는 요구사항이 있었다. `domain.SupplierClient`라는 인터페이스(포트)를 두고 각
공급사가 구현체(어댑터)로 붙는 구조를 택하면, 답이 자연스럽게 나온다 —
*"`supplier/{new}/`에 구현체 하나만 추가하면 되고, `domain`·`application`은
안 건드린다."*

완전한 헥사고날(`adapter/in`, `adapter/out` 풀 네이밍)은 과제 규모(7일, 핵심 흐름
위주) 대비 과하다고 판단해, `supplier/`, `web/`처럼 익숙한 이름을 쓰되 포트-어댑터의
본질(인터페이스 하나 + 구현체 여럿)만 가져왔다.

**대안으로 검토했던 것**: 기술 계층형(`controller/service/repository/dto`) —
`dto/` 밑에 여러 공급사 DTO가 뒤섞여서 "이게 어느 공급사 거였지"를 매번 찾아야
하는 문제가 있어 기각.

## 매핑 테이블: 왜 이 스키마인가

**요구사항**: 같은 공급사 상품은 조회할 때마다 항상 같은 내부 식별자로 돌아와야 함.
객실 타입 코드는 숙소 안에서만 유일함 (다른 숙소에 같은 코드가 존재할 수 있음).

- `hotel_mapping`에 `UNIQUE (supplier, external_hotel_code)`를 건 이유: 이 제약이
  없으면 매핑 upsert 로직이 애플리케이션 레벨에서만 중복을 막게 되는데, 동시성
  문제(매핑 갱신 배치가 겹쳐 돌 경우)에 취약하다. DB 레벨 제약으로 안전하게
  보장하는 쪽을 택함.
- `room_type_mapping`의 유니크 키를 외부 숙소 코드가 아니라 **이미 발급된 내부
  `hotel_mapping_id`**로 잡은 이유: 외부 숙소 코드로 조합하면 "숙소 코드 + 객실
  타입 코드" 문자열 조합 키가 되어 인덱스 효율이 떨어지고, 정규화 원칙(FK로
  연결)에도 안 맞는다.
- 공급사가 다르면 같은 실제 숙소라도 내부 식별자를 공유하지 않는 것이 **기본
  동작**: 두 공급사 상품을 하나로 합치는 "중복 상품 병합"은 안내 문서에서 선택
  구현으로 명시했고, 병합 여부 판단(숙소명 유사도 등) 자체가 별도 설계 과제라
  1차 범위에서 제외.

## 스키마 관리: 왜 Flyway인가

`ddl-auto: update`는 빠르지만 "왜 이렇게 스키마를 바꿨는지"가 코드에 안 남고,
운영 환경에 그대로 쓰면 위험하다는 인식을 보여주기 어렵다. Flyway 마이그레이션
파일은 그 자체로 스키마 변경 이력이 되고, 각 파일을 커밋 단위와 맞추면 "왜 이
컬럼/인덱스가 필요했는지"가 히스토리에 남는다.

## Mock Supplier: 왜 별도 포트인가

애플리케이션과 같은 포트에서 Mock을 띄우면 앱이 자기 자신을 HTTP로 호출하는
구조가 되어, 스레드 풀이 묶이면서 실제 연동 문제와 구분이 안 되는 실패가
발생할 수 있다 (안내 문서에서도 명시적으로 경고). 9090 등 별도 포트로 분리해
원인 추적을 단순하게 유지.

## WebClient: 왜 RestTemplate/RestClient가 아닌가

과제 요구사항에서 명시적으로 WebClient를 지정함 — 다수 공급사를 동시에
호출하는 흐름에서 타임아웃·재시도·병렬 호출 제어를 어떻게 다루는지를 보기
위함. WebFlux 전면 도입은 요구되지 않아, MVC 위에서 WebClient만 사용하는
방식으로 결정 (전체 WebFlux 스타터 대신 `spring-webflux` 단일 의존성만 추가).
