# 의사결정 자동 기록

이 프로젝트는 "과정"이 평가 대상이다 (JOURNAL.md, AI 활용 기록). 설계 판단이 있을
때마다 아래를 수행한다 — 사용자가 매번 "저널에 남겨줘"라고 요청하지 않아도 된다.

## 기록 대상

이 스킬은 두 종류를 구분해서 다룬다 — **결정**과 **가정**은 성격이 다르다.

- **결정**: 두 가지 이상의 유효한 접근법 중 하나를 우리가 의도적으로 선택한
  경우 (예: 요금 필드를 총액 필수+일자별 선택으로 하기로 함). 스펙이 정답을
  요구하지 않는 영역에서 "우리가 고른 것".
- **가정**: 스펙(부록 A)이 애초에 명시하지 않아서, 그 공백을 우리가 해석해서
  채운 경우 (예: 매핑에는 있는데 응답에 없는 객실 타입을 어떻게 처리할지 —
  스펙이 이유를 안 알려주므로 우리가 해석해서 처리 방식을 정함). **나중에
  스펙 해석이 틀렸다고 밝혀지면 수정 대상이 될 수 있는 항목.**

판단 기준: "이걸 다르게 해도 스펙 위반이 아닌가?"(→ 결정) vs "스펙에 이 상황
자체가 안 나와 있어서 우리가 추측해야 했나?"(→ 가정). 애매하면 가정 쪽으로
분류한다 (더 보수적으로 — 나중에 재검토 대상임을 명확히 하기 위함).

기록 트리거는 아래 중 하나에 해당할 때:
- 결정: 두 가지 이상의 유효한 접근법 중 하나를 선택한 경우, 검토했지만
  채택하지 않은 대안이 있는 경우, `docs/*.md`의 "열린 질문"/"진행 중" 항목이
  해결된 경우
- 가정: 스펙에 명시 안 된 상황을 마주쳐서 우리가 해석/처리 방식을 정한 경우
- 공통: Claude(AI)가 제안한 방향을 사용자가 그대로 받아들이지 않고 수정하거나
  거부한 경우

## 기록 형식

`JOURNAL.md`의 현재 `## Day N` 섹션(없으면 새로 추가) 아래 `### 의사결정`에 추가:

```
- **[결정 요약]** — [선택한 것과 이유를 1~2문장으로]
  - 검토했다 기각한 대안: [있다면]
```

**가정**인 경우 앞에 `[가정]` 표시를 붙여서 결정과 구분한다:

```
- **[가정] [가정 내용 요약]** — [스펙이 뭘 안 알려줬는지 + 우리가 어떻게
  해석/처리했는지]
```

세션 마지막에 AI 활용이 있었다면 `### AI 활용`에 짧게 한 줄 추가:

```
- [무엇을 물었고, 그 답을 그대로 썼는지/수정했는지/거부했는지]
```

## README.md 갱신 기준

`JOURNAL.md`는 과정 전체(시행착오 포함)를 남기는 곳이고, `README.md`는 그중
**핵심만 요약**해서 보여주는 곳이다. 결정과 가정은 README에서도 다르게
취급한다.

### 가정 → 항상 README "가정" 섹션에 반영

가정으로 분류된 항목은 **예외 없이** `README.md`의 "가정" 섹션(표)에 한 줄
추가한다. 가정은 "스펙이 말 안 해준 걸 우리가 해석한 것"이라 나중에 스펙
해석이 틀렸다고 밝혀지면 재검토가 필요한데, 이런 항목이 JOURNAL 안에 묻혀
있으면 놓치기 쉽다. README 표에 모아두면 한눈에 검토 대상 목록이 된다.

표 형식(README에 이미 있는 표 그대로):
```
| [가정 내용 한 줄] | [스펙이 뭘 안 알려줬는지] — [우리 처리 방식] |
```
상세 근거가 관련 `docs/*.md`에도 있으면 표의 오른쪽 칸 끝에 링크를 덧붙인다.

### 결정 → 아래에 해당할 때만 README "설계 의사결정 요약" 반영

**README도 갱신해야 하는 경우**
- 숙소/객실/요금/재고 표준 모델의 필드나 판단이 바뀌거나 새로 확정된 경우
- 매핑 저장·생성 전략(언제 동기화하는지 등)이 바뀌거나 새로 확정된 경우
- Supplier 어댑터의 경계·실패 판정 통일 방식이 바뀐 경우
- 그 외 README에 이미 요약돼 있는 항목의 내용이 달라진 경우
- README에 아직 없지만 "인터뷰에서 나올 법한 핵심 설계 판단"에 해당하는 새 결정

**JOURNAL에만 남기면 되는 경우** (README는 건드리지 않음)
- 구현 세부사항 (변수명, 내부 헬퍼 함수 구조 등)
- 이미 README에 요약된 결정을 바꾸지 않는, 세부 구현 중 생긴 사소한 판단
- 테스트 케이스 선정처럼 README 요약 수준에는 안 맞는 세밀한 결정

**갱신 방식**: README의 해당 섹션 문장을 새로 고치거나 한두 문장을 추가한다.
근거를 길게 늘어놓지 않는다 — 상세 근거는 이미 JOURNAL/`docs/`에 있으니,
README에는 "무엇을 결정했는지 + 왜(한 줄)"만 반영하고 필요하면 관련
`docs/*.md` 링크를 함께 남긴다.

## 원칙

- **판단의 결과만이 아니라 과정을 남긴다.** "X로 했다"보다 "X와 Y를 비교했고,
  Z 때문에 X를 택했다"가 훨씬 낫다 — 안내 문서가 "시행착오가 드러나는 기록"을
  높게 평가한다고 명시했다.
- **사용자의 판단과 AI의 제안을 구분해서 적는다.** "Claude가 제안 → 사용자가
  검토 후 채택/수정"처럼 누가 무엇을 했는지 명확히 한다. 사용자의 결정을 AI의
  결정처럼, 혹은 그 반대로 적지 않는다.
- 사소한 변경(오타 수정, 포맷팅 등)은 기록하지 않는다. 기록 대상은 "왜 이렇게
  했는지 나중에 설명할 수 있어야 하는" 판단으로 한정한다.
