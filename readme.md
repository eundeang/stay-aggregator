# Stay Aggregator

여러 숙박 공급사(Supplier A, B ...)의 상품을 하나의 내부 표준 모델로 통합해
검색할 수 있게 하는 백엔드.

## 빌드 및 실행

**사전 요구사항**: JDK 21, Docker(Docker Compose 포함)

**방법 1 (권장, 한 번에)**

```bash
./dev-up.sh
```

MySQL 기동 → Mock Supplier를 백그라운드로 기동하고 응답 확인될 때까지 대기 →
애플리케이션을 포그라운드로 기동(Ctrl+C로 종료 시 Mock도 함께 종료)까지
한 번에 처리한다.

**방법 2 (수동, 각각 별도 터미널)**

```bash
# 1. MySQL 기동
docker compose up -d

# 2. Mock Supplier 기동 (별도 터미널, 포트 9090)
./gradlew :mock:bootRun

# 3. 애플리케이션 기동 (또 다른 별도 터미널)
./gradlew bootRun
```

- DB: MySQL 8.4, `stay_aggregator` (Docker Compose로 로컬 기동)
- Mock Supplier는 본 애플리케이션과 다른 포트(9090)에서 별도로 뜬다 — 같은
  포트에 두면 자기 자신을 호출하는 구조가 되어 실제 연동 문제와 구분이 안 되는
  실패가 생기기 때문.

## 기술 스택

Kotlin · Spring Boot 3.4+ · Gradle(Kotlin DSL) · MySQL · Spring WebClient
(Supplier 연동 전용) · Flyway (스키마 마이그레이션)

## API

### 숙박 상품 검색

```
GET /api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
```

```bash
curl "http://localhost:8080/api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0"
```

보유한 전체 숙소를 대상으로 Supplier A/B를 병렬 조회해 표준 모델로 통합한
결과를 반환한다. 지역/키워드 필터·정렬·페이징은 비범위(아래 "비범위" 참고).
일부 공급사가 실패해도 나머지 결과는 그대로 반환되며, 실패 사유는 응답의
`partialFailures`에 공급사별로 기록된다(`TIMEOUT`/`RATE_LIMITED`/
`NO_MAPPING_DATA` 등 — 전체 목록: `docs/supplier-adapter.md`).

Swagger UI: 앱 기동 후 `http://localhost:8080/swagger-ui.html`

## 설계 의사결정 요약

상세 근거는 `docs/` 아래 각 문서 참고. 여기서는 핵심만 요약한다. 요구사항 문서가
"판단해서 근거를 남겨라"라고 요구한 개별 항목의 진행 상태는
[`docs/judgment-checklist.md`](docs/judgment-checklist.md)에서 추적한다.

### 1. 숙박 상품 통합 모델

Supplier A(일자별 단가, 세금 별도)와 B(숙박 전체 총액, 세금 포함)의 표현이
겹치지 않아, 무엇을 표준으로 삼고 무엇을 버릴지 판단이 필요했다.

- **숙소/객실**: 물리 객실이 아닌 "객실 타입" 단위 (두 공급사 모두 이 단위로만
  제공). `(공급사, 외부 코드)`는 매핑 조회용 키일 뿐, API 응답의 `hotelId`/
  `roomTypeId`는 이 키로 실제 발급된 내부 PK(Long)다 — 공급사 원본 코드가
  응답에 그대로 노출되지 않도록 함. 공급사가 다르면 실제로 같은 숙소라도
  별도 식별자를 가지는 것을 기본 동작으로 함(중복 병합은 미구현, 선택
  구현으로 남김).
- **요금**: 총액(세금 포함)을 필수 필드로, 일자별 단가는 선택 필드(null 허용)로
  설계. 두 공급사가 100% 채울 수 있는 값이 총액뿐이라 이를 필수로 삼았고, B에
  없는 일자별 단가를 억지로 추정하는 대신 있는 그대로(없으면 null) 노출해
  정보를 조작하지 않는 쪽을 택함.
- **재고**: N박 전체 예약 가능 객실 수 = 기간 내 일별 재고의 최솟값. 체크인일만
  보거나 평균을 내면 실제로는 예약 불가능한 상품을 가능하다고 잘못 노출할 위험이
  있어 최솟값으로 판정.
- **예약 불가 상품**: 응답에서 제외하지 않고 `0`으로 노출 — 클라이언트가 매진
  표시 등에 활용할 수 있도록 정보를 선제적으로 제거하지 않음.
- **잃은 정보**: B의 일자별 단가·세금 상세(원본에 없음), 두 공급사 간 동일
  숙소 여부(공통 키가 스펙에 없어 판단 근거 부재 — 병합은 선택 구현으로 보류).

→ 상세 필드 정의와 각 판단의 전체 근거: [`docs/domain-model.md`](docs/domain-model.md)

### 2. 매핑 저장 전략

요금·재고는 원본이 외부에 있어 저장하지 않고, 공급사 코드 ↔ 내부 식별자
매핑만 DB에 저장한다. 숙소 목록은 자주 안 바뀌고 재고·요금은 매번 바뀌는
성격 차이를 반영한 설계. 매핑 동기화는 **앱 기동 시 1회(블로킹)**만
수행한다 — 검색 요청 시점 트리거, TTL 지연 갱신, 외부 배치/크론 등 7개
대안을 비교한 뒤 이 프로젝트 규모엔 가장 단순한 방식으로 결정. 전국
숙박업 규모(3~5만 건)를 가정한 배치 upsert 최적화(멀티로우 `INSERT ...
ON DUPLICATE KEY UPDATE`)도 반영돼 있다.

→ [`docs/architecture.md`](docs/architecture.md)

### 3. Supplier 연동 어댑터

WebClient로 각 공급사를 호출하고 도메인 모델로 변환하는 계층을 두되, 공급사
전용 DTO가 도메인 계층으로 새어나가지 않도록 "공급사 중립 값 객체"라는 중간
계층을 추가로 뒀다. A(HTTP 상태 코드)와 B(HTTP 200 + resultCode)의 서로 다른
실패 표현은 어댑터 내부에서 동일한 실패 사유 타입으로 통일한다.

→ [`docs/supplier-adapter.md`](docs/supplier-adapter.md)

### 4. Mock Supplier

요구사항 문서 스펙대로 정상/장애/무응답 3가지 상황을 재현하도록 구성. 실제
공급사 API는 호출하지 않는다.

→ [`docs/mock-supplier.md`](docs/mock-supplier.md). 요구사항 문서
원문은 이 저장소에 포함하지 않는다.

## 가정

요구사항 문서가 명시하지 않아서, 설계·구현 중 우리가 해석해서 채운 부분들.
스펙 해석이 틀렸다고 밝혀지면 수정 대상이 되는 항목이라 "결정"과 구분해서
관리한다.

| 가정 | 근거 / 처리 방식 |
|---|---|
| 매핑에는 있지만 재고·요금 응답에 없는 객실 타입의 처리 | 이유(인원 초과 필터링인지, 다른 사유인지)를 스펙으로는 구분할 수 없음 — 이유를 추측하지 않고 "공급사 응답에 실제로 있는 것만 결과에 포함"이라는 단순 원칙으로 통일. 재고 `0`으로 채워 넣지 않고 결과에서 제외 |
| 공급사 API 타임아웃 값(connect 2초/response 4초) | 공급사 응답 시간에 대한 SLA가 스펙에 없음 — 일반적인 웹 서비스의 체감 대기 한계(수 초 이내)와 "연결 실패는 응답 지연보다 더 빨리 포기해도 된다"는 원칙으로 값을 판단(실측 아님). 상세: [`docs/architecture.md`](docs/architecture.md) "타임아웃 값" |
| 검색 API 요청 파라미터 유효성 기준(checkOut은 checkIn 이후, adults 1 이상, children 0 이상) | 스펙에 파라미터 유효성 규칙이 명시돼 있지 않음 — 날짜 역전·인원 0명 이하 같은 무의미한 조합이 서비스/DB까지 내려가지 않도록 컨트롤러 경계에서 400으로 거부하는 최소한의 구조적 제약만 적용(과거·미래 날짜 제한 등은 추가하지 않음) |

→ 별도 설계 근거가 필요한 항목은 관련 `docs/*.md`에도 상세를 반영한다
(위 표의 두 번째 항목 참고).

## 테스트

도메인 계산 로직과 어댑터의 DTO 파싱·실패 판정처럼 스펙이 확정된 부분은
TDD(Kotest FunSpec)로 작성했다. 오케스트레이션처럼 구현하며 세부가 정해지는
부분은 구현 후 통합 테스트로 검증했다.

- **공급사 어댑터 공통 계약 테스트**: 신규 공급사를 추가할 때 실패 판정
  6종·인증 헤더 등 기본 계약을 빠뜨려도 아무도 못 잡는 문제를 막기 위해,
  `supplierClientContract` 테스트 하네스로 공유해 공급사마다 다른 DTO 파싱만
  각자 작성하면 되게 함.
- **Konsist 아키텍처 테스트**: "domain은 다른 계층을 모른다", "공급사 DTO는
  `internal`" 같은 구조 규칙이 시간이 지나며 조용히 깨지는 걸 막기 위해
  `ArchitectureTest.kt`가 계층 의존 방향·DTO 가시성 등을 커밋마다 정적으로
  검증한다.

→ 진행 로드맵: [`docs/tdd-roadmap.md`](docs/tdd-roadmap.md)
